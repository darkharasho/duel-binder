# Binders Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let users build per-game binders from rules and hand edits, track completion against a per-binder goal and languages, sync them, and show them to friends.

**Architecture:** One shared repo (`src/main/repo/binders*.ts`) runs on all three clients, as the wishlist does. Rules compile to printing-level SQL; a pure function turns the matched printings, ownership and hand edits into slots. Sync copies the wishlist: tombstones, latest edit wins, one seq per table on the server.

**Tech Stack:** TypeScript, React, Electron, better-sqlite3 / OPFS SQLite / Durable Object SQLite, vitest.

**Spec:** `docs/superpowers/specs/2026-11-01-binders-design.md`

## Global Constraints

- Branch from `origin/main`, never local `main`, which is 148 commits behind.
- Append migrations; never edit a shipped step. Next desktop version is 30.
- API changes are additive only. New sync routes must tolerate a 404 from an older portal.
- Portable references only: `pkey` for printings, `card_id` for cards, `image_id` for art. Never a printing `id`.
- Every catalog query uses unary `+game` on `cards`, `card_printings` and `card_images`.
- No compound SELECTs on the server. Pass lists as one JSON value with `json_each`.
- No test data of 100k+ rows; benchmark in a standalone script.
- Tests: `npm test -- <path>` and `npm --prefix workers/portal test`, which already cap workers at 2.
- User-facing word is "binder". "Collection" means a user's whole collection.
- End every commit message with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **A rule from a newer app reaches an older one.** The binder stays readable, is not rewritten, and shows "Update the app to edit this binder". (Task 1, Task 8)
2. **A binder is deleted on one device while another adds a hand edit.** Nothing crashes, the binder stays deleted, and the orphan edit is ignored. (Task 5, Task 8)
3. **A never-signed-in desktop user signs in.** Their binders and edits move to the account; none vanish. (Task 8)
4. **A friend goes private or stops being a friend while a binder is open.** The next request returns nothing and leaks no name or card. (Task 9)
5. **A rule matches a huge share of the catalog**, such as Rarity = Common. The form says to narrow it, and neither the app nor the Worker stalls. (Task 3, Task 10)

### Task 4: Slot builder

**Files:**
- Create: `src/main/repo/binderSlots.ts`
- Test: `tests/main/binderSlots.test.ts`

**Interfaces:**
- Consumes: `BinderGoal`, `BinderEditLevel`, `BinderEditAction`
- Produces a pure function with no database access:

```ts
export interface SlotPrinting { pkey: string; printingId: number; cardId: number; listed: boolean
  qualifies: boolean; added: boolean; price: number | null }
export interface SlotImage { imageId: number; cardId: number; sortOrder: number }
export interface SlotCopy { pkey: string; cardId: number; imageId: number; quantity: number }
export interface SlotEdit { level: BinderEditLevel; target: string; action: BinderEditAction }
export interface Slot { key: string; level: BinderEditLevel; cardId: number; imageId: number | null
  printing: SlotPrinting | null; owned: number; added: boolean; price: number | null }
export interface SlotResult { slots: Slot[]; ownedSlots: number; missingSlots: number
  valueToFinish: number; unpricedMissing: number }
export function buildSlots(goal: BinderGoal, printings: SlotPrinting[], images: SlotImage[],
  copies: SlotCopy[], edits: SlotEdit[]): SlotResult
```

`listed` is false for contributed or hidden printings. `qualifies` means the printing passes the rules. `added` means it is there only because of a hand edit's card or printing.

Rules, in order:

1. Printing and card removals drop those printings from every step; a removal beats an add at the same or a broader level.
2. `card`: one slot per card with a listed, qualifying printing or a card/printing add.
3. `art`: one slot per image of a card with a listed, qualifying printing, or of an added card. An added printing makes the art slot of a copy on that printing if one exists, otherwise a card slot. Art removals drop the slot.
4. `printing`: one slot per listed, qualifying printing. An added card expands to all its listed printings in any language. An added printing makes one slot, even if unlisted.
5. `none`: one card slot per card with an owned copy on a qualifying printing, plus every added card or printing; `missingSlots` and value are 0.
6. Filling: a rule slot fills from a copy on a qualifying printing, listed or not. An `added` slot fills from any copy of its target. An art slot also needs a matching `imageId`. An added card the rule already matches keeps its slots but counts as `added`.
7. A missing slot's price is the lowest non-null, positive price of its eligible printings. `valueToFinish` sums them; `unpricedMissing` counts those with none. Prices only count once per slot, and owned slots contribute nothing.

Reads share one private `loadSlots`. If `matchedPrintingCount` exceeds `MAX_BINDER_MATCHES`, it returns `tooBroad: true` with no slots, and `saveBinder` still saves, so a catalog that grows past the cap can't lose a binder. The form blocks saving a new too-broad rule (Task 12).

Orphan edits (no live binder) are ignored by every read. `removeBinder` tombstones the binder and its edits in one transaction, one statement per row as `settleWishlist` does. `action: null` tombstones the edit row. `saveBinder` rejects a non-`editable` binder with a `CollectionError`, and rejects over `MAX_BINDERS` or `MAX_BINDER_EDITS`.
